# Azure Ontology Lab: 개발 계획

기준일: 2026-11-06. 이 문서는 현재까지의 대화와 다중 모델 검토를 개발 작업으로 정리한 **계획**입니다. 문서의 Git 게시 승인은 아래 미확정 설계·예산·배포의 일괄 승인을 뜻하지 않습니다.

## 1. 목표와 범위

복잡한 비정형 문서에서 업무 개념과 근거 있는 사실을 만들고 정형 데이터와 연결합니다. Azure/Microsoft 네이티브 기능을 우선 사용하되 직접 구현·운영 책임을 드러냅니다. 온톨로지 생성, RAG 구현, 평가 파이프라인과 팀 공유용 상세 가이드·결과 보고서까지 연결합니다.

| 상태 | 결정 |
|---|---|
| 확정 | 프로젝트명 Azure Ontology Lab, 목표 저장소명 `azure-ontology-lab` |
| 확정 | N 네이티브 RAG, F Fabric 온톨로지/Graph RAG, H HorizonDB Graph RAG, M Microsoft GraphRAG를 구현·비교 대상으로 유지 |
| 확정 | 문서 기반 온톨로지 구성과 TBox·ABox·근거·정합화·질의·답변·운영 평가 포함 |
| 확정 | E1 발견, E2 승인 스키마 기반 추출, E3 그래프 기여 통제, E4 전체 구성 비교를 분리 |
| 확정 | E3는 동일 추출 사실의 비그래프 검색/그래프 조회 최소 한 쌍. N의 E1·E2는 N/A |
| 확정 | 계약과 금융 PDF를 처음부터 포함. 금융은 FinanceBench를 대상으로 권리·표본 확인 후 사용하며 계약과 별도 보고 |
| 수행됨 | GPT·Claude·Gemini·Grok 계열 5개 모델의 독립 검토 5건과 동료 검토 5건, 설계 문서 반영 |
| 검토 대기 | 소형 합성 정형 테이블과 계약 문서를 연결하는 시험 |
| 검토 대기 | 평가 세부 방식, 운영 시험, 구성·실험별 gate와 승인 역할 |
| 미정 | 데이터 버전·문서/질문 수·분할·독립 정답, 주 지표·판정 기준·예산·담당자·구독·지역·Preview 허용 |
| 차단 | 원격 저장소 rename은 HTTP 403으로 미완료. 현재 원격명 `document-ontology-azure-poc` 유지 |

네 대상이 모두 배포 가능하다고 가정하지 않습니다. 기능·권한·예산 때문에 실행하지 못하면 사유와 증거가 있는 `blocked`로 남깁니다. 성공 결과나 0점으로 바꾸지 않습니다.

## 2. 데이터와 정답 계획

| 트랙 | 초기 후보·입력 | 평가 용도와 추가 작업 |
|---|---|---|
| 계약 | CUAD 원문, LegalBench-RAG 근거 검색, ContractNLI 의미 판단 | 공개 태스크를 각각 재현. 중복·계약 계열을 확인하고 작은 독립 TBox/ABox 정답 영역을 별도 작성 |
| 금융 PDF | FinanceBench 공개 QA와 대응 원문 PDF | 표·수치·단위·기간·근거 페이지 평가. 금융 의미 모델·사실 정답 범위는 별도 정의 |
| 정형 연결 제안 | 계약 ID·회사 ID·검토 상태·기준 시점의 합성 관리 표 | 정답 조인, 동명이인, 연결 불가, 시점 불일치와 양쪽 원천이 필요한 질문 작성. 승인 전 미확정 |

공개 데이터셋은 비정형 원문과 일부 과업 정답을 제공하는 자산이지 완성된 온톨로지 정답이 아닙니다. 금융 공개 QA도 교차 문서·전체 종합·금융 TBox/ABox의 정답으로 자동 전용하지 않습니다.

취득 전에 코드·주석·원문 각각의 이용 조건과 모델 입력·재배포 범위를 확인합니다. 허용되지 않은 원문은 Git에 넣지 않고 취득 절차·버전·체크섬을 남깁니다. 평문 문자 오프셋과 PDF 페이지·영역은 분리하며, 정렬 실패를 평가 분모에서 숨기지 않습니다.

계약과 금융의 문서 수·질문 수·점수를 합쳐 하나의 우승 점수로 만들지 않습니다. 금융·계약 각각의 대표성과 정답 범위를 보고합니다. ViDoRe, 한국어 전이, 추가 온톨로지 벤치마크는 승인할 확장 후보입니다.

## 3. 개발 단계와 완료 조건

아래 작업 분해는 실행안입니다. 미확정 세부 항목은 해당 작업 착수·평가 고정 전에 확인합니다. 일정을 임의로 정하지 않으며 pilot 이후 비용·인력·표본 규모를 산정합니다.

| 단계 | 개발 작업·산출물 | 의존 관계·완료 조건 |
|---|---|---|
| P0: 실행 조건 | 제품/API/모델 버전·지원·지역·관리형/직접 구현 명세, 승인 역할·예산 초안 | 문서 조사부터 가능. 유료 호출·생성은 예산·접근 승인 후. 구성별 필수 기능과 차단 사유 기록 |
| P1: 데이터 pilot | 계약·금융 취득 절차, 권리 기록, 해시·중복·분할 목록, PDF/평문 분석 표본 | 해당 이용 승인과 입력 확보. pilot 비용·오류·변동 기록, 최종 평가 자료와 분리 |
| P2: 평가 계약 | 실험 참여표, CQ, 도메인별 의미 모델·주석 규칙·독립 정답, 지표·실패 규칙·통계·조정 한도 | P1의 표본 근거와 담당자 승인. 평가 정답을 시스템 입력·조정 자료에서 분리 |
| P3: 공통 온톨로지 | 문서 분석 → TBox 후보 → 사람 승인 → ABox 추출 → 정합화·근거·시간·제약 검사 | E1/E2의 조건 구분. 버전·출처·손실·실패가 추적되고 채점 가능해야 함. 품질 미달도 평가 대상 |
| P4-N: 네이티브 RAG | Foundry IQ/AI Search 경로, 검색·인용·답변과 실행 기록 | 해당 입력·기능·안전 조건 확보. 그래프 파생 사실·커뮤니티 요약을 N 입력에 넣지 않음 |
| P4-F: Fabric | 문서 추출 자료의 테이블 매핑, 온톨로지/Graph 구성, 원문 검색·질의 연결 | 지원 기능·권한·용량 확인. 포털 수작업·refresh·의미 손실·연동 제약 기록 |
| P4-H: HorizonDB | 지원되는 AI Functions·AGE·벡터 경로와 답변 연결 | Preview·지역·필수 운영 조건 확인. 미지원 기능은 가정하지 않고 차단/직접 구현 범위 기록 |
| P4-M: Microsoft GraphRAG | 버전 고정 라이브러리, Azure 실행·저장, 선택한 검색 모드 | 관리형 제품과 오픈소스 운영 책임 구분. 원본 흐름과 수정 어댑터를 다른 구성으로 기록 |
| P5: E3 최소 비교쌍 | 동일 고정 추출 사실의 레코드 검색과 그래프 조회, 공통 생성·근거 접근·예산·추적 | P2와 채점 가능한 P3 사실 필요. 통제 불가능하면 해당 증분 주장을 보류 |
| P6: 본 평가·운영 | E1~E4 실행, 도메인별 원시 결과·신뢰구간·실패·지연·비용, 변경·삭제·ACL·복구 시험 | 해당 실험의 정답·설정 고정과 안전 조건 충족. 미응답·재시도·초기 적재 비용도 기록 |
| P7: 공유·재현 | 개념 가이드, 구성별 따라 하기, 비교 보고서, 선택 기준, 운영·정리 절차 | 원시 결과와 주장 연결. 비작성자가 서면 절차로 실행 또는 blocked 진단을 재현 |

P4-N/F/H/M은 접근·데이터·평가 조건이 갖춰진 구성부터 독립 진행할 수 있습니다. 공통 P3를 쓰지 않는 N이나 제품 자체 흐름의 E4에 P3 완료를 강제하지 않습니다. P6도 모든 구성이 성공할 때까지 기다리는 전역 잠금이 아닙니다. 자세한 gate 제안은 [방법론 §9](methodology.md#9-실행-순서와-중단-기준)에 있습니다.

## 4. 평가 파이프라인 개발안

실행 명세 → 권리·입력·정답 분리 확인 → 구성별 실행 → 표준 결과·원시 추적 저장 → 공식/자체 평가 → 통계·오류 분석 → 보고서 순서로 연결합니다.

각 결과에는 실행·구성·실험·도메인·질문 ID, 데이터/스키마/프롬프트/코드/모델 버전, 답변·근거·경로, 요청 상태, 지연·호출·토큰·비용을 연결합니다. 비밀 값이나 허용되지 않은 원문을 기록하지 않습니다.

E1은 개념·관계 발견, E2는 승인 스키마 아래 사실·정합화·근거, E3는 고정 사실 아래 조회 증분, E4는 자연스러운 제품 전체 흐름을 평가합니다. E4 순위로 그래프 구조만의 인과 효과를 주장하지 않습니다.

TBox/ABox와 PDF 분석·검색·답변·운영 점수는 구분합니다. 공식 평가기는 고정 버전 그대로 재현하고, 근거 지지·제약 위반 등 추가 검사는 보조 결과로 분리합니다. 부분 정답에 없는 관계는 자동 오답으로 간주하지 않습니다.

LLM 심판은 보조 수단이며 사람 검토·독립 정답을 대체하지 않습니다. 주 지표·최소 의미 차이·문서 계열 단위 분석·반복·실패 점수는 본 평가 전에 고정합니다. 차이가 불확실하면 미결론으로 보고합니다.

## 5. 운영 시험과 최종 산출물

운영 시험안은 문서 추가·정정·삭제, 근거 일부 삭제, ACL 회수와 파생 사실·요약·캐시 노출, 부분 실패·재실행, 변경 반영·복구·비용을 포함합니다. 지원 기능과 직접 구현, 증분 반영과 전체 재구축을 구분합니다. 세부 요구는 사용자 검토와 실제 운영 정책 확인 후 고정합니다.

최종 산출물은 실행 코드·허용된 샘플/취득 절차·배포 설정·평가 실행기·버전 명세·원시 결과·비교 보고서·상세 가이드입니다. 구현·운영 검증 전에는 제품 적합성이나 결과를 확정하지 않습니다.

현재 완료된 것은 계획·방법론·검토 문서입니다. 데이터 취득, 독립 정답 작성, Azure 배포, 구현, 평가·운영 측정은 미실행입니다. 다음 개발 착수 전에는 검토 대기 항목과 구독·권리·예산·담당자를 확인해야 합니다.

상세 설계: [방법론과 실행 계획](methodology.md). 비평의 출처·한계·반영 이력: [다중 모델 검토](methodology-review.md).
